# Доступ к UI Дирижёра (`/ui/`) — карта, threat model, rollout

Статус: **P3a-3, черновик от 17.11.2026 (исполнитель DeepSeek).**
Публичный ingress **не применялся**. Изменения кода — только опциональный
безопасный профиль приложения и тесты; ждут ревью интегратора Kimi.

**Итог одной строкой:** защищённого публичного URL для `/ui/` **сейчас нет**.
Существует только loopback `http://127.0.0.1:9310/ui/` на DE-1 и эфемерный
Cloudflare Quick Tunnel, направленный на MCP-шлюз `:9320` — `/ui/` через него
**не отдаётся** (проверено: 404). Пользоваться дашбордом с телефона/ПК без SSH
сегодня нельзя.

---

## 1. Фактическая карта доступа (проверено на DE-1, 17.11.2026)

| Компонент | Где | Слушает | Снаружи | Аутентификация |
|---|---|---|---|---|
| Дирижёр API + `/ui/` | DE-1, `src/api.py` | `127.0.0.1:9310` | нет | **нет** (рассчитан на loopback, AD-6) |
| MCP-шлюз ChatGPT | DE-1, `src/mcp_server.py` | `127.0.0.1:9320` | через туннель | OAuth 2.0 + консент-секрет владельца |
| Cloudflare Quick Tunnel | tmux на DE-1 (не systemd) | `→ 127.0.0.1:9320` | да | на уровне шлюза (`/mcp` = 401) |
| Docker nginx-proxy | DE-1 | `:80/:443` | да | относится к VPN/Remnawave-контуру; Дирижёра **не проксирует** |
| Host nginx | DE-1 | Debian default (docker-proxy занял порты) | — | Дирижёра не проксирует |

### Статические факты (получают интегратор и владелец)

- `/ui/`, `/ui/app.js`, `/ui/app.css`, `/orders`, `/stats` **— только на loopback**.
- MCP-шлюз публикует **только** `/mcp*` (OAuth) и `/mcp-consent`; `/ui/`,
  `/orders`, `/stats`, `/approvals/open` на нём отдают **404** — UI не опубликован
  и случайно открыть его наружу нельзя.
- Корневой путь Quick-туннеля (`/`) отдаёт 404, `/mcp` — 401 (ожидаемо: без
  токена MCP не пускает).

### Замеры HTTP (локально, без секретов)

```
GET  http://127.0.0.1:9310/ui/          200  (text/html, страница дашборда)
GET  http://127.0.0.1:9310/ui           200  (редирект/отдача на со слэшем)
GET  http://127.0.0.1:9310/orders       200  (анонимно — это loopback)
GET  http://127.0.0.1:9320/ui/          404  ← UI не проксируется шлюзом
GET  http://127.0.0.1:9320/orders       404
GET  http://127.0.0.1:9320/mcp          401  (OAuth)
```

Внешняя проверка публичного хоста — только «idle» GET-запросы без параметров
авторизации, без вывода тела, чтобы не фиксировать секреты/клиентские id:

```
GET https://<quick-tunnel-host>/ui/    404
GET https://<quick-tunnel-host>/mcp    401
```

> ⚠️ **Важный вывод для владельца:** Quick Tunnel — это эфемерный адрес
> (генерируется заново при каждом рестарте), а точный публичный URL
> MCP-шлюза **не публичен** и здесь не приводится намеренно. Для интерактивного
> дашборда, который владелец открывает ежедневно, Quick Tunnel — не решение
> (меняющийся адрес). Он годен только для одноразовой проверки связи.

### Что именно мешало бы открыть UI наружу?

1. У API **нет слоя аутентификации** — она делегирована loopback. Любой прокси
   без собственной авторизации = публичное чтение задач, целей заказов, логов
   шагов и **анонимный доступ к мутациям** (`POST /orders/*`, `approve/reject`).
2. UI изначально **read-only** (`GET /orders`, `GET /orders/{oid}`; JS не шлёт
   POST), но API на том же origin отдаёт мутации — прокси должен их отсекать.
3. Quick-туннель без Cloudflare Access пускает **кого угодно, у кого URL**.
   URL утекает в логи, историю браузера, прокси. Без IdP/Firewall-правила это
   публичный доступ.

## 2. Threat model (кратко)

| Угроза | Вектор | Последствие | Контрмера в плане |
|---|---|---|---|
| Публичное чтение очереди | открытый URL `/ui/` + `/orders` | утечка целей заказов, имён репо, логов шагов | IdP на прокси (Cloudflare Access), пустой Allow (deny by default) |
| Анонимные мутации | прокси пропускает всё | approve/reject/pause/retry чужаком | профиль `public_ui_only=True` → 403 на всё, кроме read-GET; на прокси ещё и метод-фильтр |
| Перебор/кража доступа | утечка Quick-туннеля, weak link | чужой доступ к дашборду | Cloudflare Access + 2FA владельца, короткий TTL сессии |
| Утечка секретов в браузер | UI получит токен в JS | компрометация kredenshelов | токены остаются на прокси/IdP; в браузер не попадают |
| DNS-rebind / SSRF | агрессивный клиент шлёт поддельный `Host` | обход host-фильтра | профиль read-only + `Host` расставляет туннель, SDK-регистрация не публикуется |
| IP DE-1 в публичных репутациях | открытый туннель на боевой VPN-ноде | риск блокировок, спам | без надобности не публиковать; при публикации — Cloudflare Access и только `/ui/` |
| Случайно опубликовать loopback-API | кто-то направит туннель на `:9310` без auth | полная компрометация Дирижёра | **только** через прокси с auth; добавить проверку в ревью (см. чек-лист) |

Принцип: **«API остаётся loopback; наружу — через прокси, который умеет
аутентифицировать и режет мутации»**. Ничего не выкладываем в публичный DNS
без IdP.

## 3. Что подготовлено в этом шаге (без публикации)

- `src/api.py`: `build_app(..., public_ui_only=False)` + middleware
  `_public_ui_read_only`. При `True` пропускаются только:
  `GET/HEAD /` `/ui` `/ui/` `/ui/*` `/orders` `/stats` `/approvals/open`.
  Всё остальное (POST-мутации, SSE `/api/v1/events`) → `403 {"error":"public_ui_read_only"}`.
  Значение по умолчанию `False` — **production-поведение не изменилось**.
- `tests/test_ui_access.py`: фиксирует карту доступа и контракт профиля
  (трафик, мутации, SSE, HEAD, редирект `/` → `/ui/`).

Проверка:

```bash
cd /matrix/dirigent
.venv/bin/python -m pytest tests/test_ui_access.py -q
.venv/bin/python -m pytest tests/ -q           # весь набор
```

Результат прогона 17.11.2026:
- `tests/test_ui_access.py` — **12 passed** (10 контрактных + 2 на CLI-флаг `--public-ui-only`).
- Полный набор `tests/` (`HOME=/root GOCACHE=… GOPATH=…`) — **152 passed, 0 failed**.
  Ранее «2 failed» были только из-за окружения агента (нет `$HOME`/`GOCACHE`);
  с заданным окружением Go-чекеры проходят. Регрессий от правок нет.

Реализовано в этом шаге (без изменения production):
- `src/api.py`: `serve(..., public_ui_only=False)` — параметр для отдельного
  read-only инстанса; по умолчанию боевой профиль не меняется.
- `src/cli.py`: `dirigent api --public-ui-only` (+ вынесен `build_parser()`),
  флаг по умолчанию `False`, слушает `127.0.0.1`.
- `tests/test_ui_access.py`: 3 теста на CLI (парсинг флага, default off,
  проброс в `serve()`); все проходят без поднятия туннеля.

> **Статус производства не тронут.** Боевой инстанс на `:9310` и Quick Tunnel
> (`→ :9320`) не перезапускались; публичный ingress не применялся.

## 4. Путь к запуску (для ревью Kimi; не применять до одобрения)

**Вариант A — рекомендуемый: Cloudflare Tunnel (named) + Cloudflare Access.**

Почему: домены Cloudflare уже используются (Quick Tunnel), можно ограничить
доступ email-списком владельца + one-time-pin, а туннель — постоянный адрес.

Требуется от владельца (зависимости, не действия исполнителя):
1. Домен (уже есть) и аккаунт Cloudflare с управлением DNS.
2. Созданный named-tunnel и его токен — **в vault**, не в git, не в tmux-history.
3. В Cloudflare Access: приложение на `dash.<домен>`, политика `Allow` **только**
   email владельца, OTP-логин; все остальные — deny.
4. Разрешение интегратора Kimi на изменение production-конфигурации/туннеля.

Минимальный конфиг (эскиз, в репозиторий не кладём секреты):

```yaml
# ~/.cloudflared/config.yml на DE-1
tunnel: <TUNNEL_ID>
credentials-file: /matrix/secrets/cloudflared-tunnel.json   # vault, chmod 600
ingress:
  - hostname: dash.<OWNER_DOMAIN>
    service: http://127.0.0.1:9311        # отдельный инстанс (см. ниже), НЕ 9310
  - service: http_status:404
```

Запуск отдельного **read-only** инстанса API для публикации (не трогая боевой
`:9310`, который работает под systemd/tmux Дирижёра):

```bash
DIRIGENT_PUBLIC_UI=1 .venv/bin/python -m src.cli api --port 9311 --public-ui-only
```

> Реализация флагов `--public-ui-only` / `DIRIGENT_PUBLIC_UI` в `src.cli` —
> следующий шаг (в этом шаге мы не меняли CLI). До неё публичный профиль
> доступен только из кода/тестов.

**Вариант B — Cloudflare Access поверх Quick Tunnel** (быстрая проверка,
только на время, не постоянный): Quick Tunnel не даёт стабильного hostname и
Access его не защищает; **не рекомендую** для ежедневного дашборда. Только
как ручную проверку «страница открывается».

**Вариант C — за VPN-контуром DE-1 (xray)**: доступ только с устройств с
уже выданным VPN-профилем; нет нового публичного DNS. Плюс: минимальный риск.
Минус: телефон/ноутбук должны быть онлайн в VPN. Если владелец готов — это
самый безопасный «нулевой» вариант: проброс nginx на `127.0.0.1:9311` внутри
VPN-сети.

## 5. Rollout-чек-лист безопасности (для ревьюера/оператора)

- [ ] Прокси слушает `127.0.0.1` и поднимается **только** через tunnel/proxy.
- [ ] Домена/токены Cloudflare лежат в vault; в git `git grep` секретов == пусто.
- [ ] Cloudflare Access: единственная политика `Allow` для email владельца,
      2FA/OTP включён, сессия ≤ 24 ч; `Bypass`-политик нет.
- [ ] На прокси явно запрещены не-GET методы на `/orders*`, `/approvals*`.
- [ ] Инстанс для публикации — профиль `public_ui_only=True` (тесты:
      `tests/test_ui_access.py::test_public_profile_blocks_*`).
- [ ] Проверка с чужого браузера/инкогнито: `/ui/` → логин IdP, без токена — 302/401.
- [ ] Проверка приватности: `/orders`, `/stats` без сессии — отказ (302/401), не 200.
- [ ] Проверка, что `POST /orders` через публичный URL → 403/405 (не создаёт заказ).
- [ ] Healthcheck: ежедневно `GET https://dash.<домен>/ui/` без сессии → 3xx (IdP),
      логировать, не раскрывать тело.
- [ ] Логи прокси не содержат query-строк с токенами.
- [ ] Откат: остановить tunnel/expose-юnit → `/ui/` снова только loopback;
      `src/api.py` по умолчанию не публикует ничего.
- [ ] После отката — проверить, что `127.0.0.1:9310` работает как раньше.

**Решение принимает интегратор Kimi.** Если одобрение не получено — ничего в
production не меняется, `/ui/` остаётся локальным.

## 6. Инструкция пользователю (владельцу)

### Сегодня (без SSH и без публикации)

Открыть дашборд можно **только на самом DE-1**:
`http://127.0.0.1:9310/ui/` — либо через SSH-проброс:
`ssh -L 9310:127.0.0.1:9310 <de1>` и затем `http://localhost:9310/ui/` в браузере.
С телефона этот путь не работает (нужен SSH/туннель).

Сейчас браузер показывает: список заказов, деталку заказа с DAG шагов и
инспектор узла. Мутаций нет (только чтение), SSE нет.

### После одобрения (как это будет выглядеть)

1. Владелец получает адрес вида `https://dash.<домен>/ui/`.
2. Открывает с телефона/ПК → экран Cloudflare Access → вводит свой email →
   OTP из почты (или IdP) → видит дашборд.
3. Логина/пароля Дирижёра нет: авторизует прокси (IdP). Секрет Дирижёра
   браузеру не выдаётся. Выход — «Sign out» в Access.

### Чего делать НЕ надо

- Не направлять Quick Tunnel на `127.0.0.1:9310` «на минутку» — API без auth.
- Не публиковать URL/скриншоты с доменом в публичных чатах.
- Не хранить токен Cloudflare в git/tmux-history — только vault.
