# Registry routing — незакрытые зависимости (для решения Kimi/владельца)

Собрано по фактам этого заказа. Ничего из списка не блокирует тесты модуля,
но влияет на «включить в демон по-настоящему».

## 1. Gemini авторизация не подтверждена (нужно разрешение владельца)

Факты probe на DE-1 (без платных проб): `gemini` 0.68.0 установлен;
`~/.gemini/settings.json` → `security.auth.selectedType=gemini-api-key`;
файл `~/.gemini/gemini-credentials.json` **не парсится как JSON** (формат CLI
не подтверждён), `apiKey` в settings нет, env пуст.

⇒ `probe.gemini = installed=True, authenticated=False, available=False`.
Для подключения Gemini нужен **один** smoke-запуск `gemini -p "ok"` с
разрешения владельца (это и единственный способ закрыть неизвестность).
Если CLI при этом работает через уже существующую подписку/ключ — это
единственная проверка, платный API отдельно не дёргаем.

## 2. Tier-2 квота Codex (WP-8) не реализована

`quota_used/quota_limit` всегда `None`. Пока это так:
- UI не должен рисовать «% квоты» из registry;
- `exhausted` восстанавливается только из факта запуска (`launch_result` в audit);
- после `reset_at` Codex допускается как «последний шанс» — см. `docs/registry.md`.

## 3. Провал флага Codex на живой квоте (из WP-2, не закрыт)

`--approve-for-me` в `codex-cli 0.167.2` не проверен на живой квоте
(`src/executors/codex.py`, комментарий). Это внешняя зависимость от окна
владельца; registry это не маскирует: класс ошибки остаётся `unknown` при
непонятном stderr.

## 4. Расхождение в машине состояний: waiting_resource только из ready

`src/states.py` не содержит `(running, waiting_resource)`, а
`src/scheduler.py:125` ставит `waiting_resource` из `running`. На практике это
означает, что базовый путь, если исполнитель не готов, оставляет шаг в
`running` до `requeue_stale` (lease 10 мин), а не «ждёт ресурс» мгновенно.

Registry-путь обходит это через `ready(force) → waiting_resource`.
**Решение за Kimi:** добавить `(running, waiting_resource)` в `_ALLOWED` (и
поправить базовый `_run_inner`) либо оставить как есть. Это правка ядра, в
скоуп этой задачи не входила.

## 5. Бюджет запусков: одновременно в попытке и в retry ядра

Реестр гарантирует ≤3 запуска исполнителей **внутри одной попытки** шага.
Если `retry.max_attempts > 1`, ядро повторит попытку (новый вызов
`reg.launch` с тем же `launch_key` — но кэш уже содержит результат, поэтому
повторного запуска не будет до `reg.forget(key)`). То есть:
- при завершении попытки «провалом» повторной попытки фактически не произойдёт,
  пока Kimi не решит очищать кэш между попытками;
- если решите очищать (`registry.forget(f"{oid}:{sid}")` в `due_retries`), то
  суммарно запусков будет ≤3×max_attempts — тогда нужен отдельный глобальный
  счётчик в `steps`/`events`.
Предложение: пока оставить как есть (безопасно: не жжёт больше), а глобальный
потолок сделать при включении P3 UI.

## 6. Audit-журнал: путь и ротация

По умолчанию `/matrix/dirigent/var/registry-audit.jsonl` (или
`DIRIGENT_REGISTRY_AUDIT`). Ротация не сделана (append-only, читается `tail`).
При активной работе нужен logrotate/размерный лимит — решение инфраструктуры
(системный юнит вне скоупа этой задачи).

## 7. Тесты `test_checkers.py::test_go_test_ok`, `test_run_acceptance_chain`

Падают **до** моих изменений на этой машине: go не находит `GOCACHE`/`HOME`
в окружении теста. К registry не относятся, но при CI будет «красный» — стоит
починить в тестовом окружении (`HOME=$TMPDIR GOCACHE=...`).
