# Dirigent — отчёт о перезапуске проекта (инвентаризация + архитектура)

Подготовлено Kimi (интегратор) по директиве ChatGPT-руководителя, 17.11 днём.
Только чтение/диагностика; платных запусков нет; активные заказы не дублировались.

## A. Факты (подтверждено реальными вызовами)

**Работает:**
- Ядро: state machine, lease/heartbeat, retry с монотонным счётчиком, квота как
  состояние (waiting_quota + reset_at), восстановление после краха, worktree-изоляция
  с merge в `dirigent/integrate`, чекеры приёмки (go_test/pytest/repo_changed-строгий/
  files_exist/artifact/diff_apply), защита от ложного «готово».
- MCP ChatGPT↔Dirigent: 17 инструментов + dirigent_call-диспетчер + notices-доска
  (двусторонний канал без курьера). Проверено вызовами через туннель.
- Telegram: тировая доставка (quiet-по-умолчанию, approval/critical до владельца,
  test/service-заказы отфильтрованы, коалесцинг). Кнопки согласований, /d*-команды.
- Веб-визуализатор: SPA (SVG-DAG, safe DOM) + SSE /api/v1/events; /ui/ 200, стримит.
- Деньги: **остаток DeepSeek $0.77 из $2** — endpoint /user/balance работает
  (проверено реальным вызовом). Списания по заказам — из usage ответов (где есть).
- Исполнители на DE-1: kimi 2.6.0, codex-cli 0.167.2 (OAuth Plus, сейчас занят
  ручным NexusBro), opencode 2.3.0 (DeepSeek), gemini 0.68.0, qwen-code 0.27.4.
- Домашний ПК: online, GPU 0%/630MiB, ollama 200.
- Хост: 6 CPU, 12GB RAM (5 свободно), диск 65G.
- 243/243 тестов на dev (после слияния M1).

**Частично:**
- Локальный LLM-supervisor: НЕТ (п.14) — scheduler исполняет статические политики,
  решения «перепланировать/переназначить» требуют внешнего мозга. Это главный пробел
  автономности: без ChatGPT система не принимает управленческих решений, только
  ретраит по правилам.
- Codex квота: достоверного программного источника нет (unofficial probe — опция,
  официально — только UI/ошибки CLI).
- Параллельные экземпляры CLI: opencode — да (отдельные процессы/конфиги-сессии),
  gemini/kimi headless — да; codex — технически да, но общая 5h-квота и риск
  конкуренции с ручной сессией владельца (нужна политика: автозадачи codex только
  при подтверждённо свободной квоте).

**Отсутствует:**
- Публичный HTTPS для визуализатора (dirigent.hipogas.org) с авторизацией.
- Учёт расходов по заказам/дням/месяцам в БД (источник данных есть, агрегации нет).
- Декомпозиция цели в DAG существует как M1 (planning.py от ChatGPT — принят в dev,
  деплой после окончания M2), но не подключена как автоматический этап create_order.
- Несколько параллельных агентов ОДНОЙ модели с разными worktree (инфраструктура
  worktree готова, пул экземпляров — нет).

## B. Почему система ещё не достигла цели

1. **Автономное управление:** нет локального supervisor-LLM — система ждёт ChatGPT
   для решений. Ночной эксперимент показал: ChatGPT спит/осторожничает → работа
   стоит. Плюс scheduler не умеет сам ставить следующие заказы из цели.
2. **Параллельность:** семафор=2 есть, но назначение исполнителей ручное
   (type в шаге ставит заказчик), а не по ресурсам/квотам/стоимости.
3. **Бюджет:** источники появились (balance DeepSeek), но политика «остановиться
   при $X» не подключена к запускам.
4. **Связь с ChatGPT:** работает, но ChatGPT не может просыпаться по событию —
   ограничение платформы; компенсация = локальный supervisor + notices.

## C. Выбранная архитектура (рекомендация одна)

**Свой ядро развиваем, Paperclip не внедряем.**
Paperclip (перепроверен по коду в начале проекта): Node 24 + embedded PG + React,
модель «компания агентов». Внедрение = замена нашего проверенного ядра за неделю
переписывания ради чужой модели мира. Что берём из него точечно: (а) идею
квота-пробы Codex (read-only, за флагом), (б) auth-кэш сессий, (в) budget hard-stop.
Наш стек остаётся: Python+SQLite+systemd — он доказал надёжность за ночь боевых
обходов (4 дефекта найдены и исправлены автономно).

Ключевое дополнение — **локальный supervisor**: фоновый цикл в демоне, раз в N минут
(и по событиям) вызывающий ДЕШЁВУЮ модель (deepseek-chat, копейки) строго по шаблону:
«состояние очереди + правила политики → решение: запустить/переназначить/эскалировать».
Пределы: только действия внутри утверждённого бюджета и политики; всё прочее —
notices ChatGPT/владельцу. Это снимает пробел автономности БЕЗ ожидания просыпания
ChatGPT и без риска дорогих решений.

## D. План (вертикальные этапы; исполнители: DeepSeek-заказы через MCP, тяжёлое — Codex при свободной квоте, ревью/интеграция — Kimi)

**E1. Учёт денег и бюджет-стоп (0.5 дня):** poller баланса DeepSeek (endpoint есть),
таблица spend_by_order/day, лимиты policy ($/день, $/заказ), pre-flight проверка
перед lease coding-шага. Приёмка: фиктивный расход учтён, при превышении лимита
шаг уходит в waiting_quota-like «budget_hold».
**E2. Supervisor-цикл (1 день):** src/supervisor.py (шаблонный промт, парсинг
строгого JSON-решения, вайтлист действий, dry-run режим). Приёмка: сценарий
«заказ error → supervisor решает retry/reroute по политике → исполнено без человека»
на mock-исполнителях.
**E3. Пул исполнителей + автовыбор (1-1.5 дня, зависит от M2 — каталог ChatGPT,
принять его работу): registry исполнителей (tag→available/cost/quota), выбор по
стоимости+доступности при создании шага; 2 параллельных opencode-экземпляра.
Приёмка: заказ с двумя независимыми шагами уходит двум экземплярам одновременно.
**E4. Авто-DAG при создании цели (0.5 дня, на базе M1): submit_goal → planning →
create_order цепочкой, без ручных шагов. Приёмка: одна цель текстом → готовый DAG.
**E5. Публичный визуализатор (1 день): dirigent.hipogas.org за reverse-proxy с
basic-auth/oAuth-lite + TLS (домен владельца уже на Cloudflare — named tunnel).
Приёмка: открытие с телефона, логин, live-обновления.
Параллельно возможны: E1∥E2, E3∥E4. Риски: codex-квота (гейтится), сетевые сталлы
DeepSeek (killpg уже есть).

## F. Главный демонстрационный тест (критерий готовности)

Сценарий «Один вечер автономии» (staging-ветка dirigent, копия БД):
1. Владелец утверждает ОДНУ цель текстом: «в pilotcalc добавить пакет stats
   (Min/Max/Avg + тесты) и CLI-обёртку».
2. E4 строит DAG (4 шага, 2 независимых), E3 назначает исполнителей, два opencode
   работают ПАРАЛЛЕЛЬНО в разных worktree.
3. В шаг №2 внедрён контролируемый сбой (mock.fail первой попытки) → supervisor
   (E2) решает retry по политике; acceptance другого шага перепроверяет результат
   первого (交叉-ревью: шаг-verify с type opencode, проверяющий diff соседа).
4. Бюджет-стоп (E1): лимит заказа $0.25, фиктивный счётчик расхода не превышен.
5. Владелец наблюдает всё в /ui/ (без единого ручного назначения), Telegram
   получает 2 сообщения: «цель принята» и «цель завершена».
6. Критерий PASS: done без единого человеческого шага после утверждения цели.
